# Технический spike: MAX Bot API (риски R1, R2)

Цель — до начала разработки MAX-канала (Спринт 7) подтвердить или опровергнуть две возможности, от которых зависит паритет функционала с Telegram. Проводится в Спринте 0, результат фиксируется в конце этого документа.

## R1 — Нативный запрос контакта
**Вопрос:** поддерживает ли MAX Bot API кнопку «Поделиться контактом» (аналог Telegram `request_contact`), возвращающую номер телефона в структурированном виде?

Проверка:
1. Зарегистрировать тестового MAX-бота, получить токен.
2. Отправить клавиатуру с кнопкой запроса контакта; проверить, приходит ли номер в апдейте.

**Fallback (если нет):** текстовый ввод номера с валидацией формата (`+7XXXXXXXXXX`), подтверждение кодом не требуется. Шаг остаётся обязательным (без контакта сценарий не открывается).

## R2 — Передача выбора из мини-приложения в бот
**Вопрос:** есть ли в MAX WebApp аналог `Telegram.WebApp.sendData(...)` для передачи `{case_id, case_type}` из React-мини-приложения в бота?

Проверка:
1. Открыть тестовое мини-приложение в MAX.
2. Проверить наличие JS-API для отправки данных боту и соответствующего апдейта на стороне бота.

**Fallback (если нет):**
- Вариант А: deep link из мини-приложения в бот с параметрами (`start=case_<id>_<type>`), бот парсит payload.
- Вариант Б: мини-приложение шлёт выбор на backend (`POST /orders`), бот подхватывает по client_id.

## Влияние на архитектуру
Общее FSM-ядро бота (`bots/core/`) канал-независимо. Канал MAX — тонкий адаптер: если R1/R2 = «нет», отличается только слой ввода контакта и приёма выбора; сценарий и статусы не меняются.
