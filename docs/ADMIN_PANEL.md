# Админ-панель (AdminUI) — анализ ТЗ, архитектура, план

Источник: ТЗ v2.0 (разделы «Роли пользователей админки», «Функции AdminUI», «БД Сообщений
от бота») + аналитический PDF. Стек: React + Vite (фронт), FastAPI (backend, единый для всех
платформ), JWT-аутентификация, PostgreSQL.

## 1. Роли (ТЗ v2.0)

Две роли (Дизайнер и Менеджер доставок объединены в одну — «Дизайнер»):

| Роль | Доступ к данным | Действия |
|---|---|---|
| **Админ** | Все таблицы без ограничений | Назначать Дизайнеров/Админов; просмотр и **редактирование всех полей**; выгрузка в Excel; управление текстами бота; управление настройками скидок |
| **Дизайнер** | БД Заказов **без** финансовых полей (Себес, Маржа, Total_discount, Стоимость доставки, Конечная стоимость); БД Чехлов **без** Себес/Маржа (только Цена для клиента) | Просмотр карточки заказа; смена статусов **«Передан в дизайн»** и **«Дизайн в процессе»**; загрузка макета (триггерит отправку клиенту); ручная отмена заказа; просмотр файлов клиента |

**Критично (безопасность):** финансовые поля скрываются от Дизайнера **на уровне API** (сериализация),
а не только в UI. Иначе данные утекут через сеть. Это ядро RBAC-модели.

## 3. Смежные правила из ТЗ (влияют на реализацию)

- **Скидки** задаются вручную в карточке клиента; `total_discount = loyal + for_slave + master_code`,
  автопересчёт при изменении любого компонента. Автоматического расчёта нет.
- **Цена чехла** = Себес + Маржа (единая для типа). Дизайнер видит только итоговую цену.
- **Загрузка макета дизайнером** — триггерная цепочка: файл → Яндекс Диск → статус «Отправка макета»
  → отправка клиенту в бот. Статус «Отправка макета» дизайнер **не** ставит вручную.
- **Отзывы**: одобренные в модерации появляются в мини-приложении и на лендинге.
- **Excel** — формат `.xlsx`, только Админ.
- **Тексты бота** редактируются без перепрограммирования (таблица `bot_messages`, коды msg_001…,
  msg_remind_1…4, msg_cancel — уже в БД).
- **Смена статусов**: Дизайнер может только «Передан в дизайн» / «Дизайн в процессе» (+ ручная отмена);
  остальные статусы — системные (webhooks/действия клиента). Матрица переходов — в `ORDER_FSM.md`.

## 4. Архитектура

**Backend** (`app/api/v1/admin/`):
- `auth` — `POST /admin/auth/login` (email+пароль → JWT), `GET /admin/auth/me`.
- `deps` — зависимости RBAC: `get_current_admin` (JWT→AdminUser), `require_admin` (роль=admin).
- Роутеры разделов: `orders`, `clients`, `case-types`, `reviews`, `bot-messages`, `broadcasts`, `users`.
- **Field-level RBAC:** ролевая сериализация — финансовые поля обнуляются/скрываются для Дизайнера
  (единый хелпер `strip_financials(order, role)`), проверяется на уровне ответа.
- Смена статусов проходит через машину состояний (`order_state_machine`) + запись истории.

**Frontend** (`frontend/apps/admin`, React + Vite):
- Аутентификация: страница логина, JWT в памяти + refresh, защищённые роуты.
- Layout: боковое меню (пункты фильтруются по роли) + топбар (пользователь, выход).
- Роутинг (react-router), API-клиент с Bearer-токеном, ролевые ограничения в UI **дублируют**
  серверные (UI — удобство, сервер — безопасность).
- Разделы-страницы: Каталог, Заказы, Клиенты, Отзывы, Тексты бота, Рассылки, Пользователи.
- Дизайн: чистый профессиональный admin-стиль (плотные таблицы, формы), фирменный акцент — точечно.
