# Верификация флоу доставки (риск R4)

**Самое слабое место ТЗ.** Сценарий (действия 3.1.9–3.1.11) предполагает: клиент выбирает службу → вводит адрес → получает **ссылку на оплату доставки от самого сервиса** (не внутри бота) → оплачивает → бот получает статус «оплачено» через API доставки → отправляет трек-номер. Нужно подтвердить, что API служб доставки вообще поддерживают такую клиент-оплачиваемую схему со ссылкой и webhook'ом.

## Что проверяем по каждой службе

| Служба | Документация | Проверить | Статус |
|---|---|---|---|
| СДЭК | https://apidoc.cdek.ru (есть) | Создание заказа, расчёт стоимости, статусы через webhook, наличие клиентской ссылки оплаты | Реализуем первой |
| Яндекс Доставка | не предоставлена | Запросить доступ и доки; поддержка клиентской оплаты по ссылке | 🔴 Блок до получения |
| Ozon Rocket | не предоставлена | Запросить доступ и доки; поддержка клиентской оплаты по ссылке | 🔴 Блок до получения |

## Ключевой вопрос к заказчику
Если API служб **не** отдают «ссылку на оплату доставки клиентом» + webhook об оплате, исходный флоу нереализуем как описано. Согласованные альтернативы:
- **Вариант A (рекомендуемый):** стоимость доставки включается в **постоплату** (рассчитывается через API службы, клиент платит одной суммой в боте); компания создаёт отправление сама, бот получает только трек и статусы.
- **Вариант B:** доставка оформляется и оплачивается на стороне компании (наложенный платёж / счёт), бот показывает трек.

## Действие в Спринте 0–1
1. Изучить доки СДЭК, подтвердить набор нужных методов (расчёт, создание, статусы).
2. Запросить у заказчика доступы и документацию Яндекс/Озон.
3. Вынести на согласование выбор варианта флоу; зафиксировать решение до Спринта 6.

Адаптеры проектируются через интерфейс `DeliveryProvider` (create_shipment / calc_cost / get_status / parse_webhook), поэтому смена флоу/службы меняет только адаптер.
