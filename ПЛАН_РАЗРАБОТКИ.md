## 1. Резюме анализа ТЗ

**Что строим (скоуп договора — только Этап 1 «Базовый»):**
- Бот Telegram + мини-приложение (WebApp) с каталогом чехлов
- Бот MAX + мини-приложение (тот же функционал)
- Лендинг (дублирует каталог, ведёт в бот через deep link)
- CRM + AdminUI: заказы, клиенты, каталог, отзывы (модерация), тексты бота, рассылки, пользователи/роли (Админ, Дизайнер)
- Полный автоматизированный сценарий заказа: контакт → каталог → тип/модель → предоплата → макет → постоплата → доставка → трек → отзыв
- Двухступенчатая оплата (предоплата + постоплата), напоминания (5м/45м/3ч/24ч) и авто-отмена через 72 ч
- Скидочная/реферальная программа (ручные скидки, total = сумма трёх компонент)
- Файлы клиентов и макеты — на Яндекс Диске

**Технологический стек (зафиксирован в ТЗ):** PostgreSQL 16, Redis 7, FastAPI, aiogram 3, React + Vite, APScheduler + Redis, VK Cloud, GitHub Actions, Sentry + UptimeRobot, Docker Compose.

**Ключевое архитектурное требование:** проектировать БД и API с заделом под этапы 2–3 (триггерные сценарии сообщений, поле ИИ-анализа в заказе), но не реализовывать их.

## 3. Архитектура (высокоуровнево)

Монорепозиторий, сервисы в Docker Compose (адаптировано под VK Cloud):

```
casetop/
├── backend/              # FastAPI: REST API + webhooks (оплата, доставка) + бизнес-логика
│   ├── app/api/          # v1: catalog, orders, clients, reviews, favorites, promo, admin
│   ├── app/services/     # order state machine, discounts, promo, notifications
│   ├── app/payments/     # PaymentGateway (Strategy): create_payment/check_status/get_webhook_payload
│   ├── app/delivery/     # DeliveryProvider (Strategy): cdek / yandex / ozon
│   ├── app/storage/      # YandexDiskClient (OAuth2, /chechlii/orders/{id}/client|design/)
│   └── app/scheduler/    # APScheduler + Redis: напоминания, авто-отмена 72ч
├── bots/
│   ├── core/             # общий FSM-сценарий, тексты из БД, канал-независимая логика
│   ├── tg/               # aiogram 3, web_app_data handler
│   └── max/              # адаптер MAX Bot API поверх core
├── frontend/
│   ├── packages/ui/      # общие компоненты: <CatalogView>, карточки, избранное
│   ├── apps/miniapp/     # Telegram/MAX WebApp
│   ├── apps/landing/     # лендинг (та же кодовая база каталога, кнопка → deep link в бот)
│   └── apps/admin/       # AdminUI (роли, RBAC на уровне API)
└── infra/                # docker-compose, VK Cloud (Object Storage, Container Registry), CI/CD
```

**Принципиальные решения из ТЗ, влияющие на архитектуру:**
- Единая FSM-логика бота, каналы TG/MAX — тонкие адаптеры (боты имеют идентичный функционал)
- Оплата через паттерн Strategy — начинаем разработку до выбора шлюза
- Тексты бота — из БД (таблица `bot_messages`), редактор в админке; схема с полем под триггерные сценарии (задел этапа 2)
- Заказ — конечный автомат на 22 статуса, переходы описаны в ТЗ (кто/авто/триггер); в модели заказа — зарезервированное поле под ИИ-анализ (этап 3)
- Клиент TG и клиент MAX — разные записи, без объединения; избранное на сервере, не синхронизируется между каналами
- Возвратов платежей нет; скидки ручные, бессрочные, `total_discount = loyal + for_slave + master_code`

## 4. Схема БД (основные таблицы)

`clients` (все поля из ТЗ: phone, tg_id/max_id, channel, промокоды, скидки, total_discount — пересчёт при изменении компонент), `case_types` (тип, кастом, себес, маржа, цена — расчётное, доступность по моделям iPhone → отдельная таблица `case_type_models`), `orders` (22-статусный FSM, материалы/макет — ссылки на Я.Диск, финансовые поля), `order_status_history`, `favorites(client_id, case_id, created_at)`, `reviews` (модерация: на модерации/опубликован/отклонён), `promo_codes` / активации, `bot_messages` (id, триггер, канал, текст, кнопки, + поле scenario_type под этап 2), `admin_users` (роли), `payments` (транзакции по шлюзам), `broadcasts` (рассылки).

RBAC: скрытие полей Себес/Маржа/скидка/стоимость доставки/итог от роли Дизайнер — на уровне API-сериализации, не только UI.

## 5. Этапы разработки

Оценки — в неделях при команде: 1 backend, 1 frontend, 1 bot/fullstack, DevOps и QA частично. Итого ~14–16 недель до приёмки.

### Спринт 0 — Подготовка и снятие рисков (1–1,5 нед.)
1. Технический spike MAX: контакт-кнопка (R1), WebApp.sendData-аналог (R2) — отчёт с вердиктом и fallback-решением
2. Верификация флоу оплаты доставки по докам СДЭК; запрос документации Яндекс Доставки и Ozon Rocket (R4)
3. Доступы: VK Cloud, Яндекс Диск OAuth-приложение, тестовые боты TG/MAX, Sentry, UptimeRobot
4. Репозиторий, ветки, code style, CI-скелет (lint + tests), Docker Compose локальный
5. Детализация схемы БД и контрактов API (OpenAPI), схема FSM заказа — на ревью заказчику

**Выход:** закрытые R1/R2, план по R4, утверждённая схема БД/API. Напоминание заказчику о дедлайне выбора шлюзов (R3).

### Спринт 1 — Фундамент бэкенда (2 нед.)
1. FastAPI-скелет, миграции (Alembic), модели всех таблиц
2. Аутентификация AdminUI (JWT), RBAC Админ/Дизайнер (включая фильтрацию полей в сериализаторах)
3. Машина статусов заказа (22 статуса, таблица переходов из ТЗ) + история статусов
4. CRUD: каталог, клиенты, заказы; расчёт цены и скидок (формулы из ТЗ)
5. Интеграция Яндекс Диск: загрузка в `/chechlii/orders/{id}/client/` и `/design/`, привязка ссылок к заказу
6. CI/CD: GitHub Actions → сборка образов → VK Container Registry; dev-стенд на VK Cloud

**Выход:** рабочий API с тестами (unit на FSM, скидки, цены), dev-стенд.

### Спринт 2 — Каталог: мини-приложение + лендинг (2 нед.)
1. Монорепо фронтенда, общий пакет UI с `<CatalogView>`
2. Мини-приложение: Каталог / О нас / Отзывы / Избранное (горизонтальная навигация), страница чехла с «Выбрать для заказа» и «В избранное»
3. Избранное — серверное, привязка к tg_id/max_id
4. Лендинг (дизайн в рамках проекта, ориентир rusuniq.ru): тот же каталог, «Выбрать для заказа» → deep link в бот; семантическая HTML-разметка (h1/h2, alt, meta) — без отдельных SEO-работ
5. AdminUI (минимум): управление каталогом (фото, название, себес/маржа, доступность по моделям)

**Выход:** каталог виден в TG WebApp и на лендинге из одного API; админ наполняет каталог.

### Спринт 3 — Бот Telegram: основной сценарий (2–2,5 нед.)
1. aiogram 3, FSM в Redis; тексты — из `bot_messages` (msg_001…msg_016)
2. Вход: приветствие → /start → запрос контакта (обязательный шаг) → главное меню (5 кнопок); распознавание постоянного клиента по tg_id/phone («С возвращением! Ваша скидка — X%»)
3. Приём `web_app_data` ({case_id, case_type}) → ветки Стандарт (имя/буква) и Кастом (фото/файлы/голосовые → Я.Диск, аудио без расшифровки) → выбор модели iPhone → подтверждение с ценой со скидкой
4. Разделы меню: «Моя скидочная программа» (ввод промокода, персональный slave-код), «Мои оплаты» (незакрытые заказы → возврат в сценарий на 3.1.3), «Мои доставки», заглушка «Поможем выбрать» (этап 2)
5. Генерация slave-кодов, валидация master-кодов, счётчики активаций

**Выход:** сквозной сценарий до момента «выставить ссылку оплаты» (сама оплата — след. спринт), E2E-прогон на тестовом боте.

### Спринт 4 — Оплата + scheduler (2 нед.) — *требует закрытого R3*
1. Интерфейс `PaymentGateway` + адаптеры выбранных шлюзов (СНГ для TG, РФ для MAX — Т-Банк предпочтительно); ссылки на оплату зависят от канала
2. Webhooks предоплаты/постоплаты → смена статусов → сообщения msg_008/msg_011
3. APScheduler + Redis: при выставлении ссылки — 4 напоминания (5м/45м/3ч/24ч) + авто-отмена 72ч; отмена всех задач при поступлении оплаты
4. Таблица `payments`, идемпотентность webhook'ов, сверка статусов (check_status) как резервный механизм
5. Кнопки «Возврат» нет (возвраты не предусмотрены)

**Выход:** предоплата и постоплата работают на тестовых контурах шлюзов; напоминания и авто-отмена проверены (с ускоренными интервалами в тестах).

### Спринт 5 — Цикл дизайнера + AdminUI заказов (2 нед.)
1. Карточка заказа в AdminUI: все поля, ролевая видимость, смена статусов «Передан в дизайн» / «Дизайн в процессе», ручная отмена
2. Загрузка макета дизайнером → триггерная цепочка: Я.Диск → статус «Отправка макета» → отправка клиенту в бот (ветка а: макет + ссылка постоплаты; ветка б: макет + «Подтвердить/Переделать»)
3. «Переделать» → статус «Пересогласование макета» (дизайнер общается вручную до нового макета)
4. Список заказов: фильтры (статус, дата, канал, клиент), поиск; выгрузка Excel (.xlsx) — только Админ
5. Карточка клиента: ручные скидки (3 поля) + автопересчёт total_discount — только Админ

**Выход:** полный цикл Стандарт и Кастом от заказа до постоплаты, управляемый из админки.

### Спринт 6 — Доставка (2 нед.) — *зависит от результата R4*
1. Интерфейс `DeliveryProvider`; первый адаптер — СДЭК (документация есть)
2. Флоу: выбор службы (Озон/Яндекс/СДЭК) → ввод адреса (дом/ПВЗ) → подтверждение + ссылка оплаты доставки → webhook «оплачено» → трек-номер → webhook «Отправлен»/«Доставлено» → уведомления
3. Яндекс/Озон — по факту полученной документации; если флоу «ссылка оплаты от сервиса» не поддерживается — реализуем согласованный с заказчиком fallback
4. После «Доставлено»: msg о прибытии → предложение нового заказа + промокод другу + уведомление о скидке → запрос отзыва → приём отзыва (текст + фото) в очередь модерации

**Выход:** полный клиентский путь до отзыва включительно (минимум на СДЭК).

### Спринт 7 — Канал MAX (1,5–2 нед.) — *по решениям из Спринта 0*
1. Адаптер MAX Bot API поверх общего FSM-ядра (или fallback-реализация контакта/WebApp по результатам spike)
2. Мини-приложение в MAX (та же React-база)
3. Платёжный адаптер РФ (Т-Банк), ссылки оплаты для канала max
4. Отдельные клиенты max_id, своё избранное, свои скидки

**Выход:** функциональный паритет MAX с TG.

### Спринт 8 — Админка: остальное + стабилизация (1,5 нед.)
1. Редактор текстов бота (все msg_XXX, кнопки), модерация отзывов (одобрить/отклонить → публикация в мини-приложении и на лендинге); редактор контента страницы «О нас» (Д2 — при подтверждении заказчиком)
2. Рассылки: ручная отправка по сегментам (канал, дата, статус)
3. Управление пользователями AdminUI и ролями
4. Sentry во всех сервисах, UptimeRobot, логирование, алерты
5. Регрессионное тестирование, нагрузочная проверка webhook'ов

### Спринт 9 — Приёмка и запуск (1 нед.)
1. Прод-окружение VK Cloud (VK Object Storage, Container Registry), секреты, бэкапы PostgreSQL
2. E2E-приёмка по чек-листу клиентского пути (обе ветки × оба канала)
3. Перенос на боевые токены ботов, боевые контуры шлюзов и доставки
4. Документация: эксплуатация, инструкция администратора и дизайнера
5. Передача заказчику, период поддержки

## 7. Definition of Done (для каждого спринта)
- Код в main через PR + ревью; unit-тесты на бизнес-логику (FSM, скидки, цены, scheduler)
- Интеграционные тесты webhook'ов (оплата, доставка) с идемпотентностью
- Развёрнуто на dev-стенде VK Cloud, пройден ручной прогон сценария спринта
- Ошибки летят в Sentry; миграции БД обратимы
- Демо заказчику в конце спринта, фиксация замечаний

## 8. Что требуется от заказчика (и когда)
1. **До Спринта 4:** финальный выбор платёжных шлюзов (СНГ и РФ) — подтверждено в ТЗ как обязательство
2. **Спринт 0–1:** документация/доступы Яндекс Доставки и Ozon Rocket; при их отсутствии — согласие на запуск только со СДЭК
